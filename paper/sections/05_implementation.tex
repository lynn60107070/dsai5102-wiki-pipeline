\section{Implementation}\label{sec:implementation}

\subsection{Stream ingestion and processing}\label{sec:impl-stream}

\Cref{tab:topics} lists the Kafka topics. The producer keeps two connections to Wikimedia. The live one
always reads from now; whenever two consecutive events are more than three seconds apart (the laptop
slept, the network dropped, Wikimedia closed the connection) or the producer restarts, the missing
interval is queued on disk. The backfill one replays each queued interval with Wikimedia's
\texttt{since} parameter, so outages fill themselves in without holding back live data. The
processor's validation, privacy and windowing logic is separated from Kafka and covered by unit tests.

\paragraph{Per-minute counts.} The processor counts edits in one-minute windows by event time and emits
a minute two minutes after it ends, so slightly late events are still counted. Its first version used
the newest event seen on any partition as the clock. While catching up on a backlog, partitions are
read unevenly, so one partition raced ahead and 205,814 events from the others were wrongly treated as
late. The fix, standard in stream processors, is a per-partition watermark: a minute closes only when
every assigned partition has passed it.

\paragraph{Delivery guarantees in practice.} Docker stops a container after ten seconds by default.
When the sinks were restarted mid-backlog, they were killed before committing their offsets and later
re-processed those events. Measured against the raw zone, the clean zone then held 381,066 duplicate
rows and no missing events. A compaction job removed every duplicate, and the stream services now get
60 seconds to shut down cleanly.

\paragraph{Outages and recovery.} The collector ran on one laptop for the whole window, so outages were
routine; \cref{tab:incidents} lists the ones that changed the design. To check the replays, we replayed
3~Nov 15:00 to 6~Nov 00:00 a second time and compared the deduplicated hourly counts: only 4,491 edits
(0.1\%) were new, and no hour of the window is empty. The only low hours, 02:00--06:00 UTC on 28~Oct,
are a real pause in bot activity.

\subsection{Batch ingestion and orchestration}\label{sec:impl-batch}

\texttt{pageviews\_hourly} runs one task chain per UTC hour: a sensor waits until the file is
published, the pageview script filters it (\cref{sec:data}), the upload writes two Parquet files to
the lake, and a clean-up step removes local copies even after a failure. Re-running an hour overwrites
the same objects, so retries and backfills are safe. The upload updates an Airflow \emph{Dataset};
\texttt{warehouse\_hourly} is scheduled on that Dataset \emph{or} hourly, so the two DAGs coordinate
without calling each other. A separate freshness check turns red when the stream has not written for
fifteen minutes.

\subsection{Warehouse and transformations}\label{sec:impl-dbt}

dbt organises the SQL in three layers (\cref{tab:schema}): \emph{staging} views over the lake,
\emph{core} facts and dimensions, and \emph{marts}, one per dashboard tile. The fact tables are
incremental: each run reloads only the last three days and replaces rows by key. Thirty-four data tests check
unique and non-null keys, accepted values, and a relationship from every fact key to its dimension.
\Cref{fig:lineage} shows how the models depend on each other.

\subsection{Reproducibility}\label{sec:impl-repro}

\texttt{docker compose up -d --build} on a fresh clone is the only step: every setting has a default,
and a one-off bootstrap service loads six bundled hours of real data into the empty lake (never into
one that already has data), runs the warehouse DAG once through Airflow, and configures Metabase
through its API. Testing this on a fresh clone found two problems, both fixed: file paths longer than
Windows allows, and a dashboard tile that failed before the stream had created its table.
