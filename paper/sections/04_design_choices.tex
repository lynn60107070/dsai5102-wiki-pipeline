\paragraph{Tools not covered in the course.} \emph{DuckDB} is an embedded, columnar SQL engine: it runs
inside the process that queries it, like SQLite, but is built for analytical scans, so the warehouse is
one file rather than a server. \emph{dbt} keeps the transformations as version-controlled SQL models whose
declared dependencies give the build order, the lineage graph and the data tests that gate the dashboard.
\emph{Metabase} is an open-source BI tool that runs in one container, chosen over Superset (more services
to run) and Looker Studio (cloud only); its API lets a script rebuild every tile.

\paragraph{Stream and batch.} Edits are a genuine event stream: they arrive continuously and cannot be
re-downloaded later, so they go through Kafka, which buffers them durably and lets several consumers
read the same events independently (the raw archive, the processor). Pageviews are published by
Wikimedia as hourly files that stay available, so a scheduled batch job is the natural fit; after downtime
Airflow catches up on the scheduled hours by itself, and a failed hour can be run again.

\paragraph{Lake zones (ELT).} The raw zone keeps every event exactly as received (schema-on-read), so
any later cleaning mistake can be redone from it. The clean zone holds validated, typed, pseudonymised
Parquet, which the warehouse reads directly without parsing JSON. Data is partitioned by
\texttt{dt=}/\texttt{hour=} so that queries over a date range only read the matching folders.

\paragraph{DuckDB computes, Postgres serves.} DuckDB is a columnar, in-process engine: it scans and
aggregates columns without a server and reads Parquet from S3
directly, which suits an analytical workload. But a DuckDB file accepts one writer at a time, so a
dashboard reading it while dbt rebuilds it would fail. The marts are therefore copied into Postgres
after every successful build, all in a single transaction, so Metabase never sees two builds at once,
and Metabase reads only those copies.

\paragraph{Star schema.} The warehouse follows a star schema~\cite{kimball2013toolkit} with three fact tables
sharing conformed dimensions: edits at the finest grain (one row per edit), linked to dimensions for time, wiki,
article and editor type, and two hourly pageview facts, per article (linked to wiki and article) and per wiki
(linked to wiki), neither yet to \texttt{dim\_time}. Natural keys replace surrogate integers because they are
stable across rebuilds; the article key is an md5 of wiki and title, so edits and pageviews join without a lookup. The four marts are each pre-aggregated for one or more dashboard tiles and store counts, not shares,
so that any date range can be summed correctly before dividing (distinct-editor counts are the
exception and are never summed across rows).

\paragraph{Reliability.} Every consumer commits its Kafka offsets only after its output is safely
written (at-least-once delivery). This can repeat events after a crash but never loses them; duplicates
are removed by event id in the compaction step and again in dbt. dbt's data tests act as a quality gate:
if any test fails, the export does not run and the dashboard keeps the last good data.

\paragraph{Privacy and access.} User names are dropped from the clean zone; only an unsalted MD5 hash
(to count distinct editors) and the editor type are kept. This is pseudonymisation, not anonymisation:
a public user name can be hashed and matched, so a salted hash is the next step, and the raw zone still keeps user names. Metabase connects with an account that can
only read the serving tables.
